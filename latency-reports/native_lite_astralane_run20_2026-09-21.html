What this test does

This is a native-transfer latency test: it sends real SOL transfers, one at a time, and times how long each takes to be observed as confirmed. Each transfer races three independent, real update channels to see which one reports it first:

  • LowLatency -- a fast, speculative processed-tier account-balance update, the earliest signal Solana exposes for a change to an account.
  • Commit -- a rooted/finalized-tier account-balance update, structurally further behind live (finality takes real time to accumulate).
  • Transaction -- a direct signature match against the transaction list itself, independent of either account-balance stream.

Whichever lane observes the expected result first wins and gets timed for that transfer -- the whole point of the comparison is seeing which lane actually wins in practice, and by how much.

20 of 20 transfers were sent as a real, tipped Astralane bundle rather than a plain send -- see the Route column below for which.

How the numbers below are calculated

Every timestamp here comes from this guest's own clock, measured against two real events: the moment a transfer is sent, and the moment one of the three lanes above reports it. Nothing in the underlying data streams carries a timestamp for the transfer's actual on-chain execution instant -- only its landing slot number -- so several of these columns are bounds, not exact measurements. The table below is a literal glossary of every column:

Total =exact
Real wall-clock time from send to whichever lane confirmed first. The only column here that's a direct measurement, not a bound or an estimate.
Write ≥lower bound
Time from send until this guest first observed the transfer's landing slot beginning. Since the transfer could have executed anywhere within that slot -- not necessarily at its very start -- the real write time can run up to roughly one Solana slot later than what's shown here.
Read ≤upper bound
Derived as Total minus Write, not measured directly. Because Write is a lower bound, Read is correspondingly an upper bound by the same margin -- an understated Write overstates Read.
Write est. ≈refined estimate
The same Write quantity above, refined using the transfer's own real Agave tx.index -- its ordinal position among every transaction in that slot's block (tx_index out of slot_max_tx_index) -- to estimate roughly how far into the slot it actually executed, rather than anchoring to the slot's start. Tighter than the plain bound wherever it resolves, but still an estimate: block execution isn't perfectly evenly spaced across a slot's real wall-clock time.
Read est. ≈refined estimate
Total minus Write est. -- the same refinement applied to Read.

Treat single-sample Write/Read splits as directional, not exact -- the est. columns (highlighted below, alongside Total) are the more trustworthy figures wherever they resolve.

Latency floor and assumptions

Two structural facts about this specific deployment set the floor under every number above:

This validator is unstaked. Solana's networking layer uses stake-weighted quality-of-service in both directions: a leader's QUIC connections favor higher-staked peers when accepting transactions under load, and a node's position in the stake-weighted Turbine tree governs how quickly it receives a new block's shreds via gossip and repair. With zero stake, this validator gets no priority TPU connection for sending and no shortened propagation path for receiving -- it's served after every higher-stake participant on the network, not because of anything about the transaction itself. That's the real cause behind the write/read split above: this guest is timing not just when a transfer landed, but when this specific, unprivileged validator found out about it.

Solana's own block cadence sets a hard floor regardless of stake. A transaction can only land once a leader actually produces a block containing it (~400ms slots), and this guest can only observe that landing once the resulting shreds physically propagate across the network to it. Neither step can be instantaneous for any validator, staked or not -- lack of stake only adds delay on top of that floor, it doesn't create it.

This is also why the test routes transfers through Astralane. Precisely because this validator has no stake-weighted advantage of its own, a plain, unassisted transaction sent directly from it competes for a leader's attention on equal footing with every other unstaked sender -- no priority, and easily deprioritized or dropped outright under any real load. Astralane is a third-party bundler/relay that maintains its own direct routes to leaders and lands transactions against a paid tip rather than against stake, so paying that tip buys back the same kind of priority a well-staked validator already gets for free (see the Route column above). It isn't chasing speed for its own sake -- it's compensating for the exact structural disadvantage described above.
