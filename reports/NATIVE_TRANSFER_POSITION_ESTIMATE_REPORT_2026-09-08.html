What this test does

testperplatencyv1lite's native-transfer test sends real SOL transfers back and forth between two wallets, over and over, alternating direction each time: Wallet 1 (the bot's own fee-paying wallet, which also covers every transaction's network fee and priority fee regardless of which direction the transfer goes) and Wallet 2 (a second wallet, deterministically derived from Wallet 1, used purely as a round-trip destination -- it never pays a fee in either direction). This run's 20 transfers all won their race via the Account/LowLatency lane and all went out via Astralane bundles.

The landing slot's own pipeline, decomposed

Every Solana slot passes through real, distinct stages on this validator, each with its own SlotStatus notification from the actual Agave geyser plugin -- not something this guest infers or estimates:

  • FirstShredReceived -- the first real network shred (Turbine) for this slot arrives here.
  • Completed -- every shred for the slot has arrived; the block is fully assembled locally.
  • Processed -- this validator has locally replayed the block -- its own local replay, unrelated to leader timing.
  • Confirmed -- real cluster-wide supermajority vote acknowledgment.

Write is measured against FirstShredReceived -- the earliest evidence this guest (a downstream validator, not the leader) ever gets that the leader saw/included the transfer. Read is everything after that: the rest of block delivery, this validator's own local replay, cluster confirmation, and this guest's own dispatch overhead, all the way until the winning lane noticed. Shred→Completed, Completed→Processed, and Processed→Confirmed are reported alongside as real, independent, informational sub-stages of what's inside that Read window -- not subtracted from anything.

New this run: a real, per-transaction position-within-block estimate

Write above is a genuine lower bound, not a point estimate: FirstShredReceived only proves a block exists, not that a specific transfer already landed in it -- shreds stream out continuously as the leader builds the block, so a transfer ordered late could really have executed well after the first shred arrived. This run adds a real refinement using Agave's own per-transaction index field (ReplicaTransactionInfo::index) -- the transaction's exact ordinal position within its landing block, already flowing end-to-end through this pipeline with zero cross-repo changes.

For each sample: fraction = tx.index / (largest tx.index this guest observed for that same slot) -- a real, honest lower bound on the block's true transaction count, never a guarantee the true last transaction was seen. That fraction is multiplied against the real measured Shred→Completed + Completed→Processed window (FirstShredReceived → Processed) and added to Write, placing the transfer's estimated real execution instant somewhere inside that window instead of only knowing it happened somewhere between the two endpoints.

This is an estimate, not a measurement -- Sealevel can execute non-conflicting transactions within a block in parallel, not strictly in tx.index order, so "later index → later execution" is a reasonable approximation, not a guarantee. Logged per transaction (not just an aggregate percentile), with the real tx.index/slot_max_tx_index inputs used, or a specific named reason when it couldn't resolve. Resolved for 16 of 20 samples this run -- see the "Est." column and its tooltip on every row.

Also fixed this run: a real send_slot staleness bug in the Slots column

A separate issue surfaced while reviewing the previous run: Slots (inclusion_slot − send_slot) showed values flatly inconsistent with real slot cadence -- one sample had slots=5 but a total of only 362ms, nowhere near enough real time for 5 slots at ~400ms each. Root cause: send_slot came from current_slot(), which only reads this guest's own SlotStatus-event bookkeeping -- and that bookkeeping can lag the real chain tip under backpressure (most visibly right at boot, behind a queued subscription/funding burst), reporting a stale slot number even though real time hadn't actually passed yet.

Fixed by tracking a second, much higher-frequency signal: the largest header.slot seen on any account/token update this guest processes (thousands per tick, each carrying its own real slot number) -- and taking the max of that against the old SlotStatus-only view. This run logged both raw signals separately at every send, to prove the fix rather than just infer it from downstream numbers looking nicer:

17 of 20 sends had gap=0 (the two signals already agreed) and the remaining 3 had only gap=1 -- nothing like the multi-slot staleness seen before. Slots until inclusion this run: p50=1, p99=1 across all 20 samples, versus p50=1/p99=2 (and one real outlier of 5) last run. write/read/total were never affected by this bug either way -- none of them read send_slot -- but Slots itself is now a trustworthy number for the first time in this test.
Real mainnet run, 20/20 landed in ~19 seconds, freshly rebuilt wasm32-wasip2 release binary carrying both fixes above. All 20 via Astralane, all 20 won by Account/LowLatency. The auto-sweep (sweep_native_wallets) queued immediately after sample 20/20 and landed on-chain on the first try again -- independently confirmed via solana confirm -v on the sweep signature (Status: Ok, mothership balance ◎0.079995 → ◎0.220437606). The known no-retry reliability gap in the sweep remains unfixed but wasn't hit this run either.
Write is a lower bound, Read is an upper bound (the raw columns below). Neither the account-update stream nor the transaction-confirmation stream carries a timestamp for exactly when inside a landing slot's block a transfer executed -- only the slot number. "Write" is measured against FirstShredReceived, not the transfer's real execution instant, so the true write time can run later than what's shown. Because Read is derived as Total − Write, an understated Write correspondingly overstates Read by the same margin. The new Est. column narrows that gap with a real per-row number, where it resolves.

Dotted/dashed values in Write ≥ / Read ≤ are a different, older same-slot estimate tier, not measurements. A same-slot sample has no resolvable Write/Read split at all -- shown with a ~dotted underline when a real upper bound exists (the estimate is that bound's midpoint), or a fainter ~dashed underline when even that bound is unavailable (falls back to this run's own median resolved Write delay). Hover either for the exact reasoning. The Est. column is independent of this tier -- a same-slot sample can still resolve a real tx.index estimate if its Transaction-lane data arrived (in this run, most same-slot samples didn't, since write_delay itself is the first required input).

Shred→Completed / Completed→Processed / Processed→Confirmed are independent, supplementary stats -- never subtracted from Read. They describe what happens to the landing slot on this validator, regardless of when this guest's own winning lane happened to notice the transfer. Processed→Confirmed is occasionally blank: cluster confirmation sometimes hasn't happened yet by the time the Account lane already has its answer, since that lane only needs local Processed state.

How each portion of the cycle is calculated

Every value below comes from real, directly-measured wall-clock Instants -- either this guest's own send-time clock, or a per-slot timestamp recorded the first time this guest sees a given SlotStatus notification for that slot (real Agave validator geyser events, not estimated). Nothing here is derived from an assumed slot-time constant.

MetricFormulaReal inputs used
Total sent_at.elapsed() This guest's own send `Instant` vs. the moment the winning lane (Account/Commit/Transaction) claimed the transfer. Always real and exact.
Write ≥ FirstShredReceived(inclusion_slot) − sent_at This guest's own send `Instant`; the first time it saw SlotStatus::FirstShredReceived for the real landing slot. A lower bound -- the transfer's real execution instant inside that slot's block can only be later.
Read ≤ Total − Write Derived, not separately measured -- inherits Write's understatement as an equal overstatement. `None` whenever Write is `None` (same-slot samples), never derived as `Total − 0`.
Shred→Completed Completed(inclusion_slot) − FirstShredReceived(inclusion_slot) Two real per-slot timestamps on this validator. Independent stat -- not part of Write/Read at all.
Completed→Processed Processed(inclusion_slot) − Completed(inclusion_slot) Same two-timestamp pattern -- this validator's own local replay time once the block was fully assembled.
Processed→Confirmed Confirmed(inclusion_slot) − Processed(inclusion_slot) Same pattern again. Frequently unresolved: Confirmed often hasn't fired yet by the time this sample is recorded, since the winning lane usually only needs local Processed state.
Write ≥ (same-slot estimate, dotted) write_bound_us / 2 Only for same-slot samples with a real upper bound (the first-observed Instant for any slot after inclusion_slot). Midpoint guess between 0 and that bound -- not a measurement.
Write ≥ (same-slot estimate, dashed) median of this run's real resolved Write values Only when even the upper bound above is unavailable. A rough prior, not tied to this specific sample.
Write Est. (per-row, this run) Write + (tx.index / slot_max_tx_index) × (Shred→Completed + Completed→Processed) Real Agave tx.index for this transfer's own transaction, and the largest tx.index this guest observed for the same slot across every transaction it saw (a real, honest lower bound on that block's true transaction count). Computed only at final-report time across all resolved samples -- not yet a per-row value.
Read Est. (per-row, this run) Total − Write ESTIMATE Same derivation pattern as Read ≤, using the refined Write estimate instead of the raw lower bound.

All timestamp inputs (send, FirstShredReceived, Completed, Processed, Confirmed, and the winning lane's own observation instant) come from the same per-slot record (SlotTimestamps), each field set once, the first time this guest sees that specific status for that slot number. tx.index and slot_max_tx_index come from the same validator's own Agave geyser plugin, captured in mid_on_tx for every transaction it sees, not just this bot's own transfers.
